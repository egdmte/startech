August 01, 2026: Wrote down why the car kept driving off the road in May. The car only knows five moves: go, back, spin left, spin right, stop. It has no way to steer gently. So when it slid a little off the line, it spun hard to fix it, went too far, spun hard back, went too far again, and kept swinging wider until it lost the line completely. The car already has the parts to steer gently (it can run its left wheels and right wheels at different speeds) - the old code just never used them that way.

August 01, 2026: ^^^ THE LINE ABOVE IS WRONG. Ignore it. We later found the real code from the competition (it is in the LEGACY folder now) and the car CAN steer gently. It has a proper smooth-steering system that is actually quite clever. The wrong guess came from reading our written report about the car instead of the car's actual code, and the report describes the car badly. Lesson: when the report and the code disagree, believe the code.

August 01, 2026: Found the real reason the car probably wandered. There is a setting that corrects for the two motors not being exactly equally strong (one is always a bit faster, that is normal for cheap motors). That setting was never measured - it was left at "no correction at all". So the car always pulled slightly to one side, and the steering brain spent the whole race fighting that pull instead of driving. There is already a tool in the project made just for measuring this, and nobody ran it.

August 01, 2026: Found two sleeping bugs in the same motor-correction code. Right now they do nothing, because the setting is switched off. But the moment somebody measures the motors properly and turns it on, both bugs wake up: the code gives BOTH wheels the left wheel's correction, and then applies the correction a second time on top. So the fix would not fix anything and would make the car slower in a lopsided way. Written down so the person who finally measures the motors does not get confused.

August 01, 2026: Found that the car's physical start button was taken out, and instead you start it by typing "GG" or "EZ" or pressing SPACE on a keyboard. This is bad for two reasons: the competition gives 50 free points for starting with a real button and no computer attached, and our own rules file specifically says the GG/EZ idea should never have been approved. The button needs to come back.

August 01, 2026: Read every file of the old competition code properly. The big surprise: the code is GOOD. The problem is that nobody finished setting it up.

August 01, 2026: Found what is probably THE reason the car wandered. The camera code needs to know which part of the picture is "the road" - you draw a shape on the image and say "this bit". Somebody changed the camera to take bigger pictures (800x680 instead of 640x480) and left a note in the code saying "warning: this shape must be re-measured for the new size". It was never re-measured. So the car was looking at a patch that is 80 pixels off to the left of where it thinks it is looking, and it cannot see the closest bit of road at all. The result: the car thinks it is off-centre even when it is perfectly centred, so it steers to fix a problem that is not there. Forever. No amount of adjusting the steering can fix that, because the steering is doing its job correctly on a wrong measurement.

August 01, 2026: Found 100 points of code that could never run. The car has a whole section for "I saw a dead-end sign, stop and turn right" - written properly, works fine. But the part that spots signs never actually tells the car what sign it saw. It is like a doorbell with no wire to the bell. So the dead-end task (100 points) was impossible to score, and the "no overtaking here" rule never switched on either. There is even a trained sign-recognising file sitting in the folder that was never plugged in.

August 01, 2026: Found a safety problem. If the camera or the vision code throws an error, the program prints the error and carries on - but it never stops the motors first. It keeps going like that for up to 30 errors in a row, which is about one whole second of the car driving blind at whatever speed it was last told. Our rules say motors must switch off on any error. The new code must brake first, then complain.

August 01, 2026: Read every single remaining file. Found the thing that actually sank the project, and it is not the code - it is the instructions ABOUT the code. There are three big "here is what we improved" documents in the old folder, all written by an AI helper in April. Almost every fact in them is made up. They say the steering setting is 0.60 when it is really 0.30. They say we should read five other guide documents - none of those five documents exist. They say the car now wobbles only 15 pixels instead of 40, and runs faster than before - nobody ever measured either number, and the change they made actually makes it slower, not faster. One of them even ends with a folder path from inside the AI's own computer. So the team went to the competition trusting a report that was confidently wrong about their own car.

August 01, 2026: New rule because of that: we only write down a speed or accuracy number if it came out of the car's own log file on a real run, with the date next to it. A guess about how well something will work is not a result.

August 01, 2026: Worked out why the motor-balance setting was never applied. The measuring tool tells you to paste "LEFT_TRIM = 0.95" into the settings file. But the settings file does not use that name any more - it was changed to four different names (slow-left, fast-left, slow-right, fast-right) and nobody updated the tool. So you could run the test, paste the answer in exactly as told, and nothing would happen at all. Fix the tool first, then trust it.

August 01, 2026: Finally answered the question that has been open since the very first notes: what "enforcement" should actually mean for SUBIRU. Wrote it up as section 22 of the plan. August 01, 2026: I made a mistake and it has been corrected. I said the motor wiring question was settled, because the code calls its two outputs "LEFT" and "RIGHT". That was bad reasoning: those are just names a person typed, not a description of where the wires actually go. The code only proves there are two outputs, not which motors are plugged into them. The schematic seems to show wires crossing between the two boards, which would mean front-and-back instead of left-and-right - and if that is true, the steering cannot work at all. August 01, 2026: Learned the car has FOUR motors, with two sharing each driver board channel. That matters because each channel can only supply about 2 amps, and two motors straining at the same time (exactly what happens going over the speed bump) will go past that and either shut down or brown out. It is worse than it sounds, because we are already feeding the motors about 175% of the voltage they are rated for, which pushes the current up too.

August 01, 2026: Found that the motor speed control is running at 100 pulses per second, which is the slow default, because nobody set it. The older version of this project set it to 1000 and that setting got lost in a rewrite. This might explain a hack in the code that forces a minimum power level - at such a slow pulse rate, low power settings produce no useful turning force. Raising the rate might remove the need for the hack entirely.

August 01, 2026: Careful note about a suggested fix. Somebody suggested adding one line to the Pi's config to enable proper hardware speed control. So it would appear fixed, change nothing, and send us hunting for the problem somewhere else. Written into the plan as something to verify on the actual Pi first, not to just paste in.
